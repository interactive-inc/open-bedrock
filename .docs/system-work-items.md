# 作業の依頼・成果確認・責任の引き継ぎ

Systemの作業記録は、依頼内容、受入条件、担当者、責任者、提出された成果と確認結果を保持する。担当者は登録済みのHumanまたはAgent、責任者はHumanに限定する。依頼者が最初の責任者になる。

## 状態と人の確認

依頼直後は`offered`、担当者の受領後は`active`、成果の提出後は`review_pending`になる。現在の責任者が成果を承認すると`completed`、差し戻すと`active`になる。中止は現在の責任者が行い、`cancelled`になる。

成果は要約と添付証拠のID・SHA-256を持つ。成果ID、依頼内容、受入条件と成果全体をdigestへ固定し、承認・差戻しはその成果IDとdigestを指定する。差戻し後の再提出では新しい成果IDを作り、古い成果を残す。成果を提出した本人は完了承認できない。

承認、差戻し、引き継ぎの依頼・受領・辞退、中止には人の短期再認証が必要である。Agentは受領と成果提出を行えるが、人の判断を代行できない。

## 責任の引き継ぎ

現在の責任者は、別のHumanへ引き継ぎを依頼できる。引き継ぎ先が受領するまで責任者は変わらない。引き継ぎ待ちの間は受領・辞退・中止と、管理者による引き継ぎ先の再指名だけを許可する。辞退は元の責任者と成果を維持する。

人のSystem管理者も引き継ぎ先を指名できる。この場合は管理者による復旧として理由と主体を記録し、指名先の受領を必要とする。責任者と引き継ぎ先が操作できなくなった場合も、管理者は新しい引き継ぎ先を指名できる。元の依頼を履歴に残し、古い引き継ぎIDでの受領は拒否する。管理者の指名だけで責任を移さない。

完了・中止後の記録は変更しない。訂正や担当者の再割当は新しい作業を作り、閲覧できる終端記録の`commandId`を`previousRevisionId`で参照する。元の依頼、成果、判断を削除しない。

## 認可と閲覧

操作にはSystemのglobal権限を使う。すべての操作に`system:work:read`を必要とし、依頼には`system:work:create`、担当者の受領・成果提出には`system:work:perform`、人の成果確認には`system:work:review`、引き継ぎ・中止には`system:work:manage`を追加する。System管理者はこれらの技術的権限を満たす。担当者や責任者への指定は技術的権限を付与しない。

閲覧は現在の責任者、担当者、引き継ぎ待ちの受領者とSystem管理者に限定する。引き継ぎ後に参加資格を失った人には、過去の依頼の再送でも履歴を開示しない。Account、Principal、権限、機械credential、再認証の現在状態を保存と開示のtransactionでも検査する。

この責任は一つの作業の受領と成果確認に関する責任である。Companyの役職、職務権限、決裁資格の変更を意味しない。Appの判断や実行許可には、[System workflowとCompany資格の合成](system-workflow.md)を使用する。

## 保存と証拠

各操作は`commandId`、期待する`expectedRevision`、理由を持つ。同じ主体・同じ正規化済み内容の再送は、現在の閲覧・操作資格を満たす場合に同じ記録を返す。同じ再送キーの別内容、古い版、並行する別操作は競合になる。

依頼、成果の版、添付の紐付け、監査を同じtransactionで保存する。監査や証拠の保存が欠ける場合、権限が途中で失われる場合は全変更を取り消す。成果の証拠には、担当者本人がSystemへアップロードした未紐付け添付、または同じ作業ですでに使用した証拠だけを指定できる。

証拠の本文は復号後に長さとSHA-256を検証し、現在の作業版、閲覧資格、添付メタデータを開示監査と同じtransactionで再検査する。監査が保存できない場合や読み出し途中で状態が変わった場合は本文を渡さない。閲覧したことを成果の承認と推定しない。

## API

`/system/work-items`に作成と一覧、`/system/work-items/:id`に詳細、`/system/work-items/:id/history`に履歴がある。一覧と履歴は最大50件ずつ取得する。

状態の変更は作業配下の`accept`、`results`、`approve`、`return`、`handovers`、`handovers/accept`、`handovers/decline`、`cancel`へPOSTする。人の判断では`x-system-step-up`ヘッダーに有効な再認証tokenを指定する。証拠の本文は`/system/work-items/:id/evidence/:attachmentId`から取得する。

## 完了の意味

`completed`は、人が指定された成果を受入条件に照らして確認した記録である。外部サービスの操作、決済、送金、Appの正本更新が成功した証明にはならない。作業の完了によってCompanyの資格やAppの実行許可を発行しない。通知配送、期限からの自動催促、複数担当者への分割、Appのチェックリストとの自動同期はこのAPIには含まれない。
