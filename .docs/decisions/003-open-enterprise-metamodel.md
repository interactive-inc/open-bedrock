# 会社を開いたメタモデルで表現する

規範性: 根拠記録。状態は accepted。後続の採択済み判断で置き換えるまで有効とする。

## 状況

`accepted`

## 判断

会社モデルを、抽象度の階層、横断する意味面、圏論的な合成規則から成る開いたメタモデルとして定義する。[三つの観点による旧判断](./002-company-system-model.md) を置き換える。

抽象度は次とする。

- 基礎存在論
- 会社共通理論
- ドメイン理論
- 個体と案件
- 内部、人間、外部への実現写像

横断する意味面は次とする。

- 存在と事実
- 意図と能力
- 規範、権限、義務
- 実行と手続き
- 主張、証拠、採用
- 技術的実現

時間、法域、文脈、版、分類、来歴は全てを横断する。

## 理由

- 新しい業務を列挙せず、型付き extension として追加できる。
- Book と ParkingSpace の固有 metadata を共通 Resource に混ぜず、Reservation など本当に共通する理論だけを再利用できる。
- 会社に必要だが製品が実行しない法律、税、給与、会計、決済を外部実現として体系へ含められる。
- 人間、AI、service、connector を Principal として統一しながら、人間承認を別能力にできる。
- Event、Assertion、Decision、Record の混同を防げる。
- domain、API、DB、外部 adapter 間の写像が意味と不変条件を保つか、可換図式として検査できる。

## 圏論の役割

圏論を会社概念の意味を決める唯一の理論にはしない。型付き概念と関係の合成、共有核を介した module 結合、schema mapping、path independence を検査するメタ言語として使う。

意味は存在論、規範理論、時間モデル、来歴モデル、ドメイン知識で定義する。並行実行、期限、暗号、安全性は状態機械、DB 制約、property test、threat analysis で補う。

## 結果

- [会社メタモデル](../company-model.md) を概念の正本とする。
- [記録・時間・来歴モデル](../records-model.md) で事実と主張を分ける。
- [権限と意思決定モデル](../authority-model.md) と [認可モデル](../authorization-model.md) を分ける。
- [AI 自動化と人間承認](../automation-model.md) で提案と実行を結ぶ。
- [外部連携モデル](../integration-model.md) で外部実現を疎結合にする。
- [ドメイン拡張規約](../domain-extension.md) と能力質問で拡張を検証する。
- 旧三観点はレビュー用の観点としてのみ残す。

## トレードオフ

- 初期の概念設計と mapping は、単一の汎用 entity より手間がかかる。
- 理論上の型と現行 table を一対一にせず、段階的な migration が必要になる。
- 圏論の表記を利用者向け説明へ露出しすぎない配慮が必要になる。
- 完全性を閉じた列挙ではなく、反例へ応答できる拡張手続きとして定義するため、継続的な検証が必要になる。
