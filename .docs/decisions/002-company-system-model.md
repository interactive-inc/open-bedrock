# 会社システムを三つの観点で説明する

規範性: 根拠記録。状態は superseded。後続の採択済み判断と仕様正本を優先する。

## 状況

`superseded`

後続の [会社を開いたメタモデルで表現する](./003-open-enterprise-metamodel.md) が本判断を置き換えた。

## 当時の課題

人、時間、物、お金、成長を排他的な最上位分類にすると、一つの業務が複数分類へまたがる。画面や既存機能を会社モデルにすると、組織改編と機能追加のたびに意味が変わる。任意属性だけの汎用 entity にすると、同一性と不変条件を検証できない。

## 当時の判断

会社を次の三つの問いで説明した。

- 業務能力: 会社が何を達成する必要があるか
- 共通意味モデル: 何について事実を持つか
- 横断統制: 誰がどの条件で扱い、どう証跡を残すか

人、時間、物、お金、成長は複数選択可能な説明タグとした。

## 有効だった点

- 五軸をデータ所有境界にしなかった。
- capability、意味、control を区別する必要性を示した。
- 未知の業務を一つの固定分類へ押し込めない方針を作った。
- 法務、税、会計などを製品境界の外部実現として考える入口を作った。

## 置き換えた理由

三つは存在論上の layer ではなく、異なる設計質問だった。そのため次を十分に区別できなかった。

- Kind、Role、Phase
- 対象、出来事、状態、関係、情報
- 事実、主張、評価、採用
- 規範、会社上の権限、技術的認可
- 判断行為、判断結果、判断記録
- 定義と実行案件
- 内部実現、人間運用、外部製品

また、AI Principal と人間承認、外部 API mapping の合成則を体系的に検査できなかった。

## 現在の扱い

業務能力、意味、統制という三つの問いは、レビュー観点として残す。会社モデルの階層としては使わない。人、時間、物、お金、成長も検索と説明の tag として残し、同一性、schema、認可、所有境界を決めない。
