# open-karte

## ジョブ(顧客が片付けたいこと)

- 社員: 申請の提出や承認、ナレッジ検索、目標管理、キャリア申告などの社内手続きを一箇所で済ませたい
- 上長や管理者: 組織と個人の状態を俯瞰し、承認や評価、1on1の記録を効率よく回したい
- 経営者: 会社の状態を記録と数字で把握し、意思決定とその根拠を残したい
- AI エージェント: CLI から会社の記録を読み書きし、足りない業務やデータを見つけて整備したい

## ビジョン

従業員台帳を土台に、会社の管理部門(総務・人事・情シス・経営管理)の業務を1つのセルフホスト基盤で網羅し、人も AI も同じ操作で会社を運営できるようにする。

## 解決する問題

- 人材データ、申請ワークフロー、[[features|ナレッジ]]、評価、キャリアが別々の仕組みに散らばっている
- 業務ごとに SaaS が増えてデータが分断され、AI から一括で扱えない
- 権限が大雑把で、評価や等級のような機微データを安心して載せられない

## ターゲット

- 社員: 日常の社内手続きを行う一般利用者
- 上長や管理者: 承認、評価、組織把握を担う利用者
- 経営者: 会社全体の状態把握と意思決定を担う利用者
- AI エージェント: CLI 経由で全業務を代行・整理する利用者

## 原則

- AI ネイティブ。全ての業務は api と karte コマンドから実行できる状態を保つ。web は人間向けの補助インタフェースであり、CLI でできないことがあってはならない
- 権限は deny-by-default。ロールは permission の集合として動的に定義し、必要なものしか見えない状態を保つ。詳細は [[roles-and-permissions|ロールと権限]]
- 扱うのは事実の記録・更新・検索と申請ワークフローまで。壊れたときに実害が出る計算・判定・実行は持たない。線引きは [[002-money-boundary|お金の線引き]]
- 新しい業務は全体地図の基本パターンの組合せとして設計し、既存ドメインと同じ4層で実装する

## やらないこと

- 事業ドメイン。販売・顧客管理(CRM)・在庫・製造・調達など、事業そのものの運営は扱わない。詳細は [[003-corporate-scope|事業ドメインを扱わない]]
- 給与計算、税額計算、仕訳・会計処理、支払の実行など、誤りが金銭損害に直結する計算と実行
- 労務・税務の法的判定。判断の前提となる知識はドキュメントとして持つが、判定はしない
- 金額を含む事実の記録は排除しない(経費・ポイント・給与改定の記録は扱う)

## 全体地図

管理部門の業務を領域ごとに網羅し、1項目ずつ実装方針を記す。この地図が守備範囲の正であり、ここに無い業務を思いついたらまずここに追記して分類する。記号の意味は次のとおり。

- 済: 実装済み(実装の正は api/src/domain と api/src/interface)
- 予定: 実装する
- 汎用: 専用ドメインは作らず、申請テンプレート(動的フォーム)で賄う
- しない: 実装しない(理由を併記)
- 外部: 外部の専門サービスに委ねる(理由を併記)

### 基本パターン

あらゆる管理業務は次の5パターンの組合せに還元できる。新しい項目を「予定」にするときは、まずどの組合せかを決める。

- 台帳: 事実のマスタを持ち、登録・更新・検索する(従業員、部署、資産)
- 申請承認: 状態遷移をともなうワークフロー(申請、休暇、経費)
- 記録: 時系列に積み上がるイベント(打刻、1on1、監査ログ)
- 割当: 人とものの対応づけ(シフト、研修受講、貸出)
- 集計: 台帳と記録を横断して数える(ダッシュボード)

例。[[ringi|稟議]]は申請承認+記録、取引先管理は台帳+記録、資格管理は台帳+割当。

### 人・組織

- 済: 従業員台帳 / 組織・部署・組織図 / レポートライン / アカウントとロール(IAM)
- 予定 異動履歴: 部署・職位の変更を時系列で記録する(記録)
- 予定 在籍イベント履歴: 入社・休職・復職・退職の履歴(記録)
- 予定 兼務: 1人が複数部署に属する実態を org で表現する(台帳)
- 予定 等級・昇格履歴: 等級マスタと昇格の記録。機微データのためスコープ権限と項目出し分けの後(台帳+記録)
- 予定 採用(応募者管理): 候補者台帳と選考ワークフロー。社外の個人情報を含むため権限基盤の後(台帳+申請承認+記録)
- 予定 表彰・懲戒の記録: 機微データ。権限基盤の後(記録)
- 汎用 副業・兼業の届出 / 通勤経路変更 / 在宅勤務申請: 申請テンプレートで足りる

### 時間

- 済: 打刻・勤怠 / 月次サマリ / 休暇と残数 / シフトと交代
- 予定 会社カレンダー: 休日・営業日の台帳(台帳)
- 予定 勤務形態の属性: [[flextime-sei|フレックスタイム制]]や[[sairyo-rodo-sei|裁量労働制]]などの区分の記録。制度の適法性判定はしない(台帳)
- 予定 時間外の集計表示: 残業時間の集計は出すが、[[36-kyotei|36協定]]への適合判定はしない(集計)
- 外部 勤怠の法定判定・給与への連携: 判定を誤ると法令違反に直結するため労務・給与サービスへ

### 成長・評価

- 済: 目標と評価 / 評価サイクルとフォーム / スキル / 1on1 / 研修 / キャリアシートと社内公募 / サーベイ / オンボーディング
- 予定 等級との接続: 評価結果と昇格の記録を繋ぐ。等級(人・組織)とセット(記録)
- 予定 評価の開示制御: 確定まで本人非公開にする制御。項目出し分けが前提
- 予定 360度評価: review の評価者種別の拡張
- 予定 資格・免許の台帳: 有効期限の記録つき台帳。更新要否の判定はしない(台帳+割当)

### 労務手続き

事実の記録と申出のワークフローのみを扱い、給付額の計算や法的判定は持たない。

- 済: 証明書発行依頼 / ライフイベント届 / 産休・育休・介護休業 / 出張 / 退職手続き / 反社チェック / 横断閲覧(6ドメインの admin 一覧。人事・監査向け)
- 予定 労務の代理処理: 申出の状態を人事が代理で進める操作 permission(横断閲覧は済)
- 予定 健康診断の実施記録: 実施日と受診済みかの記録のみ(記録)
- 予定 労災・事故の発生記録: 起きた事実の時系列記録のみ(記録)
- しない 健診・ストレスチェックの結果保持: 要配慮個人情報であり、漏えい時のダメージが大きすぎる。実施管理までにとどめ、結果は医療機関・専門サービス側に残す
- しない マイナンバー管理: 特定個人情報。法定の安全管理措置が重く、漏えい時のダメージが最大級。専門サービスへ
- 外部 社会保険・雇用保険の電子申請: 申請そのものは労務サービスへ。手続きの進捗記録は汎用テンプレートで持てる
- 外部 年末調整の計算: 計算・判定は税務へ。提出状況の進捗記録は予定(テーブルは既にある)

### お金

記録まで。線引きの基準は [[002-money-boundary|お金の線引き]] を参照。

- 済: 経費申請と承認 / サンクスポイント(原資・残高・交換)
- 予定 稟議: 金額と決裁ルートつきの汎用決裁。経営の意思決定記録の入口でもある(申請承認+記録)
- 予定 予算枠の記録: 枠と消化の記録・集計まで。会計とは繋がない(台帳+集計)
- 予定 給与改定履歴の API 化: 事実記録のみ。テーブルは既にある(記録)
- 汎用 慶弔金・見舞金の届出: 支給の事実記録は申請テンプレートで
- しない 減価償却などの会計計算: 会計ドメインそのもの
- 外部 給与計算 / 会計・仕訳 / 支払実行 / 請求書発行 / 税: 誤ると回復不能な実害が出る

### 物・場所

- 済: 備品と貸出 / 会議室予約 / 貸与品(鍵・入館証・デバイスを含む)
- 予定 ライセンス・SaaS アカウント台帳: 更新期限の記録つき台帳。情シス業務(台帳)
- 予定 座席・駐車場などの予約: 会議室と同型。必要になったら(台帳+割当)
- 汎用 名刺・物品の購入依頼: 依頼と承認は申請テンプレートで。発注・支払は外部
- しない 在庫管理 / 購買(調達): 事業ドメイン。[[003-corporate-scope|事業ドメインを扱わない]]

### 情報・文書

- 済: ナレッジ / アンケート / 通知 / 感謝
- 予定 社内アナウンス: 全社周知の記録と既読管理(記録+通知)
- 予定 規程集: 就業規則などの版管理(台帳+記録)
- 予定 文書台帳: 契約書などの所在と期限のメタデータ台帳。ファイル本体は当面外部ストレージ(台帳)
- 外部 電子契約(締結): 法的効力を伴う。締結済み文書の期限管理は文書台帳で

### 情シス

- 済: アカウントと動的ロール / 権限管理 / デバイス管理(備品でカバー) / セキュリティ教育の受講(研修でカバー)
- 予定 インシデント記録: 障害・事故の時系列記録(記録)
- 予定 アクセス権の棚卸: 誰が何を見られるかの一覧と定期レビュー。監査ログ閲覧とセット(集計)
- 汎用 PC 持ち出し・権限付与の申請: 申請テンプレートで

### 経営

- 済: 目標管理
- 予定 経営ダッシュボード: 在籍数・退職率・評価分布・申請の滞留など管理部門 KPI の集計。汎用ダッシュボードはあるが経営向けの集計が未整備(集計)
- 予定 稟議・決裁: お金の項を参照
- 予定 会議体と議事録: 定例会議の台帳と議事録の記録(台帳+記録)
- 予定 目標ツリー: 全社→部門→個人の階層。goal の拡張(台帳)
- 予定 意思決定記録: 会社の決定と根拠を ADR 形式で記録し、AI が判断の文脈として参照する(記録)
- 予定 人員計画: 要員数の計画と実績の記録・集計(台帳+集計)
- しない 株主名簿・登記・取締役会の法定議事録: 法定帳簿であり、不備の実害が大きい。専門家の管理へ
- しない 予実管理(会計連動): 会計ドメイン。予算枠の記録までにとどめる

### 対外(取引先・法務)

- 済: 反社チェック
- 予定 取引先台帳: 反社チェック・契約記録の親になるマスタ(台帳)
- 予定 契約記録: 契約日・期間・更新期限の事実記録。中身のレビューや法的判定はしない(台帳+記録)
- しない 顧客管理(CRM)・商談管理: 事業ドメイン。[[003-corporate-scope|事業ドメインを扱わない]]
- しない 与信判断: 判断は金融・調査会社へ。調査した事実の記録は反社チェックと同型で持てる
- 外部 契約書レビュー・電子契約の締結: 法務・電子契約サービスへ

### 基盤

- 済: 認証 / 動的ロールと権限 / 監査ログの記録と閲覧 / 申請テンプレートの動的フォーム / CLI からの全操作 / 通知
- 予定 スコープ権限: self・reports・department・all の4段階。機微データ拡充の前提で最優先。[[roles-and-permissions|ロールと権限]]
- 予定 項目単位の出し分け: 従業員台帳に等級・評価系の項目を載せる前提条件
- 予定 ファイル添付: 経費の領収書、証明書の交付物など
- 予定 機械用トークン: AI や自動化がログインなしで叩くためのサービスアカウント
- 予定 データエクスポート: セルフホストの出口保証。全台帳の一括出力
- 予定 動的フォーム機構の共通化: application と survey の重複解消。汎用テンプレートで賄える範囲を広げる

### コアと補足

機能には濃淡がある。コアは従業員台帳を軸にした人・時間・お金・成長の記録と申請承認で、どの会社でも必要になり、外すと製品が成立しない。補足はあると運用が豊かになるが、会社によっては使わない選択ができ、ロールの権限で丸ごと隠せる。サイドバーもこの区分に従い、コアを上、補足を下、管理を最後に並べる。

- コア: 認証と権限(IAM)、従業員台帳、組織、申請ワークフロー、勤怠、休暇、経費、評価と目標、労務手続き、通知、ダッシュボード
- 補足: シフト、スキル、1on1、研修、キャリアと公募、オンボーディング、サーベイ、感謝とサンクスポイント、ナレッジ、会議室、備品、貸与品

「予定」の項目を実装するときも、先にこの区分を決めてから作る。

### 実装の順序

機微データの安全(基盤)を先に、面の拡張を後に。

1. スコープ権限と項目単位の出し分け
2. 労務ドメインの代理処理権限(横断閲覧と監査ログ閲覧は済)
3. 稟議(経営機能の入口、動的フォームの応用)
4. 取引先台帳と契約記録(対外の土台)
5. 等級・異動履歴・在籍イベント(人事データベースの完成)
6. 経営の記録系(会議体・議事録・意思決定記録・経営ダッシュボード)

## 業務知識ベース

open-karte が扱う社内事務手続きの背景知識を、コードとは別にドキュメントとして蓄える。AI が CLI で読み書きして矛盾の検出・継ぎ足し・アナウンス作成・社内サポートに使うことを想定する。

- 用語の索引は [[glossary|用語集]]。制度用語のアトミックな定義は references/terms 配下に1用語1ファイルで置く
- 手続きの流れは [[notes/README|ノート]] の handbook にまとめる（[[入社の手続き]]・[[休暇の申請]]・[[経費精算と稟議]]・[[出張の手配]]・[[退職の手続き]]・[[ライフイベント手続き]]・[[産休・育休と介護]]・[[証明書の発行依頼]]・[[年末調整]]・[[反社チェックの申請]]）
- 法令の根拠数値は sources のサマリーに出典付きでまとめる（[[労働時間と36協定の上限規制]]・[[年次有給休暇の付与日数]]・[[源泉所得税の税率と対象]]・[[インボイス制度と仕入税額控除]] など）

制度の計算や法的判定そのものは持たない方針（やらないこと）のため、ここに置くのはあくまで判断の前提となる知識であり、給与額や税額の自動計算には用いない。

- Cloudflare Workers と wrangler: 理由: api のランタイムとデプロイ手段
- Cloudflare D1 と Drizzle ORM: 理由: api のデータ永続化
- Next.js: 理由: web のフロントエンド基盤
- Zod と zod-validator: 理由: 入力検証と型生成
