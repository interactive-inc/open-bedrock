# 添付の消去

System添付の消去は、添付ごとの暗号鍵（DEK）の破棄で行う。DEKを包んだ値をDBから消すと、object storageの原本、複製、全バックアップ世代の暗号文が同時に復号できなくなる。添付の行と暗号文は残り、業務記録からの参照と監査の対象を保つ。

## 資格

- 消去の申請と実行には、人の`personal_data:erase`または`system:admin`を要求する。機械credentialでは申請も実行もできない。
- `personal_data:erase`はどのRoleにも既定で付与しない。導入時に、会社が任命した個人情報の管理責任者にあたる人のRoleへ明示的に付与する。
- 消去申請テンプレート（完了操作`system.attachment.erase`）の作成にも、`personal_data:erase`または`system:admin`を要求する。

## 申請

- 申請の対象は、一つの添付か、一つのAccountが所有する添付の全体である。従業員を指定した場合は、Companyが従業員からAccountを解決する。
- 対象は申請時点で固定し、承認digestの対象にする。申請後に増えた添付は含めず、別の申請を要求する。
- 期限内のretentionか未解除のholdを持つ添付は対象から外し、外した添付を申請本文に記録する。対象が保全中の添付だけの場合は申請を拒否する。
- 同じ添付を含む未完了（判断待ちか承認済み）の申請がある場合、存在しない対象と消去済みの対象への申請は拒否する。
- 申請は案件の作成と同じtransactionで`system.attachment.erasure.requested`を監査に記録する。

## 判断と実行

- 判断は消去申請テンプレートの承認経路に従い、各判断を判断の保存と同じtransactionで`system.attachment.erasure.decided`として監査に記録する。
- 破棄は承認済みの案件に対してだけ実行する。判断待ち・否決・差戻し・取消の案件では実行しない。承認を経ない破棄の経路は無い。
- 最終承認の確定で破棄を実行する。最終承認者が消去の資格を持たない場合は承認済みのまま残し、資格を持つ人が専用の実行操作で確定する。
- 実行は一回限りの実行許可を消費し、DEKの破棄、案件の実行済み化、`system.attachment.key.destroyed`の監査を一つのtransactionで確定する。どれかが失敗した場合は何も残さない。
- 実行済みの案件への再実行は、破棄の監査を確認して実行済みとして応答し、二度目の破棄や監査を作らない。
- 承認後に保全された添付を含む場合は実行全体を拒否する。

## 読み出し

破棄後の添付は、暗号文が残っていても内容を返さない。DEKを包んだ値が無い添付の読み出しは失敗する。

## 復元後の再適用

DBを過去の時点へ復元すると、その後に破棄したDEKと破棄の監査がDBから戻る。破棄の監査をDBの外へ写したledgerを正本の写しとして保管し、復元後に記録済みの破棄を再適用する。再適用は包んだDEKが残る添付だけに行い、新しい破棄の判断を作らない。手順は`api/README.md`に従う。

## 責任の境界

消去請求に応じるかの判断、個人情報の管理責任者の任命、法令が求める保存・消去の要件への適合の判断は運用する会社が行う。製品が保証するのは、承認なしに鍵を破棄できないこと、破棄が必ず監査に残ること、ledgerを保管していれば復元後も破棄の状態を再現できることまでである。製品は電子帳簿保存法その他の法令への適合を判定せず、保証しない。
