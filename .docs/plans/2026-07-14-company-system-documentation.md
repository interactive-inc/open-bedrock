# 会社システム体系化ドキュメント実装計画

規範性: 非規範記録。種別は実装計画 snapshot。製品要件と実装済み状態は仕様正本、コード、migration で判定する。

この計画は完了後の判断履歴であり、会社モデル部分は [会社を開いたメタモデルで表現する](../decisions/003-open-enterprise-metamodel.md) に置き換えられた。以下の三層は当時の方針であり、現在の正本ではない。

## 目的

社内事務を対象とする open-karte の業務範囲を網羅的に分類し、五軸、共通データモデル、業務能力、認可の関係を一貫した形で記録する。

## 設計方針

- 五軸は排他的なデータ分類ではなく、画面、検索、説明に使う複数選択可能な観点とする。
- 当時は体系を業務能力、共通意味モデル、横断統制の三つの観点で説明した。
- 現状と将来像を混同せず、実装済み、部分実装、台帳のみ、未実装、対象外を明示する。
- 認可はシステム権限、組織関係、案件内の割当、状態、時点、職務分離、項目ポリシーを合成して判定する。
- 給与、税、会計、法務の重い計算や法的判断は対象外とし、その入力事実、申請、承認、証跡、外部連携は対象に含める。

## 実装項目

- 会社モデル、機能網羅表、認可モデルを正本として追加する。
- モデル採用理由と参照標準を決定記録と出典文書に残す。
- 既存の機能、利用フロー、IAM、アーキテクチャ、API 規約、用語集、バックログの説明を正本へ同期する。
- 文書形式、リンク、実装根拠、公開情報衛生、静的検査、テストを検証する。

## 完了条件

- 社内事務の対象能力と会社全体で対象外の能力が、沈黙なく分類されている。
- 新しい領域を追加するときに必要な主体、記録、時間、組織範囲、状態、証跡、認可、外部境界を判定できる。
- システムロールとマネジャー関係が分離され、認可判定で合成されることが明確である。
- UI が認可の正本ではなく、API 側の判定に従うことが明確である。
- 変更後の検査とテストが成功する。
