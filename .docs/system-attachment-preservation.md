# 添付の保全

System添付の保全は、期限まで削除を禁止する`retention`と、明示的な解除まで削除を禁止する`hold`を持つ。holdは削除停止を記録する汎用機構であり、法的義務の有無や保存年数を判定しない。

同じ添付に複数の保全を登録できる。未解除のholdが一つでもある、または未到達の保持期限が一つでもある場合は削除できない。保持期限の短縮や早期解除は許可しない。延長する場合は新しいretentionを追加する。holdの解除は指定した一件だけに適用し、他の保全を変更しない。

## APIと資格

- `POST /system/attachments/:attachmentId/preservations`は保全を登録する。
- `GET /system/attachments/:attachmentId/preservations`は保全と解除の記録を読む。
- `POST /system/attachments/:attachmentId/preservations/:preservationId/release`はholdを解除する。

すべての操作に、現在有効なHumanPrincipal、Account、globalの`system:admin`権限を要求する。登録と解除には`x-system-step-up`による短期再認証も要求する。Account、Principal、権限の付与元を読取・保存のtransactionでも照合し、変更操作では再認証の期限と失効も再検査する。同じ操作の再送でも現在の資格が必要になる。

登録の入力は`id`、`sha256`、`kind`、`retainUntil`、`reason`である。idは再送時も同じUUIDを使う。sha256はアップロード応答で確認した平文digestを指定する。holdのretainUntilはnull、retentionは登録時刻より後のUTC日時文字列にする。reasonは空白を除いて1から1000文字であり、操作主体は認証済みAccountから記録する。

解除の入力は`operationId`、`expectedRevision: 1`、`reason`である。operationIdは解除の再送時も同じUUIDを使う。未解除のholdだけがrevision 1から2へ進む。同じIDでも理由・主体・内容が異なる再送は409になる。

登録は201、同じ登録の再送と解除は200を返す。応答の`preservation`には登録内容、登録者、登録時刻、監査ID、revision、解除記録を含める。`replayed`は同じ操作の再送かを示す。登録の再送応答でも既に解除された記録を未解除とは表示しない。

一覧は`limit`を1から100、既定50とし、`cursor`でUUID順の次ページへ進む。`next_cursor`がnullならその読取時点の末尾である。異なる時刻のページを一つのsnapshotへ固定する契約は持たない。添付本体の回収後も保全と解除の記録を参照できる。

## 削除と保存

登録は、指定した添付が存在し、消去開始前で、確認したdigestと一致する場合だけ確定する。掃除対象の走査後に保全が確定しても、本体削除前のDB検査で掃除を止める。削除が先に始まった場合は保全の登録を409で拒否し、保全できたと回答しない。

保持期限の直前までは回収できず、期限ちょうどから回収できる。未紐付け添付の通常の24時間の保持条件も引き続き満たす必要がある。業務へ紐付け済みの添付を掃除対象へ追加する機能ではない。

保全を一度登録した添付は、同じIDの内容・所有者・保存先・作成日時を差し替えられない。保全中の業務への紐付けは許可する。DBの直接更新による鍵破棄・行削除も、有効な保全がある場合は拒否する。保全の登録内容と解除記録は削除・上書きできない。

登録・解除と監査は同じtransactionで確定する。監査には理由、主体、変更前後、対象digest、時刻を記録する。監査または資格の検査に失敗した場合は、保全の変更も巻き戻す。同時再送で記録や監査を重複させない。

## 適用範囲

対象はSystemの添付metadataと、そのmetadataから参照する本体である。閲覧資格を変更する機構ではなく、業務へ紐付いた添付の閲覧は従来どおり所有Appが判断する。

監査台帳自体の保持期限、App固有の外部ファイル、開示時の項目制御、バックアップ保全・失効はこのAPIの対象に含まれない。現在のmetadataから鍵を破棄しても、破棄前の鍵を含むバックアップの復号能力までは失効しない。
