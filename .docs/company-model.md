# 社内事務のために会社をどう表現するか

この文書は、open-karte が社内事務を表現するときの共通設計を定める。会社を業務能力、共通意味モデル、横断統制の三層で捉え、「人・時間・物・お金・成長」は複数付与できる検索タグとして扱う。

## 文書の位置づけ

本書は、新しい領域を追加するときに使う目標モデルである。現行機能の分類と提供面は [[capability-map|機能網羅表]]、実行時の挙動はコードを正とし、既存のテーブルや API が本書の概念をすべて実装済みとはみなさない。

既存領域は、機能変更の必要が生じた時点で本書へ段階的に合わせる。概念名を合わせるためだけの一括移行は行わず、利用者価値、データ整合性、移行可能性を伴う変更だけを実施する。

モデル選択の判断は [[002-company-system-model|会社システムを三層モデルで表現する]] に記録する。外部標準から借りる観点と採用しない範囲は [[企業モデルと認可の参照標準]] にまとめる。

## 対象と境界

open-karte は、従業員台帳を土台に、社内事務で生じる事実、関係、申請、承認、割当、記録、検索を扱う。対象には、人と組織、勤務と休暇、資産と場所、支出と予算、学習と評価、社内知識、通知、証跡が含まれる。

給与額、税額、社会保険料、仕訳、決算などの重い給与・税務・会計・労務計算と、法令適合性を確定する法的判定は外部へ委ねる。外部サービスが算出または判定した結果は、出所、取得時刻、対象、版を伴う事実として記録できる。

顧客管理、営業、販売、製品開発、製造、物流、顧客サポートなどのフロントオフィス実行系と、総勘定元帳などの会計実行系は対象外とする。社内事務に必要な取引先、契約、請求、支払の状態を扱う場合も、手続きの対象となる事実と証跡に範囲を限定する。

## 三層モデル

三層は分類の代替案ではなく、異なる設計質問に答える。業務能力は会社が何をできる必要があるか、共通意味モデルは何について事実を持つか、横断統制は誰がどの条件で扱い、どう証跡を残すかを定める。

### 業務能力

業務能力は、会社が継続的に果たす責務を表す。組織図、画面、API、個別の手順から独立させ、組織改編や実装変更があっても同じ責務なら同じ能力として識別する。

能力には、安定した識別子、名称、目的、対象範囲、上位能力、責任を負う組織単位、関連する手続き定義を持たせる。責任組織の変更は能力の同一性を変えず、能力の統合や分割は履歴を伴う明示的な改版として扱う。

能力カタログは、次の領域から構成を始める。これは固定された最上位分類ではなく、社内事務の漏れを点検するための入口である。

- 人と組織を管理する
- 勤務、休暇、予定、利用可能性を管理する
- 資産、設備、場所、利用権を管理する
- 支出、予算、契約上の約束を記録する
- 学習、スキル、目標、評価、キャリアを支援する
- 社内知識、連絡、依頼を管理する
- 規程、証跡、リスク、遵守手続きを管理する
- 外部システムとの受け渡しと運用を管理する

業務能力は処理順序を持たない。処理順序、分岐、期限、担当、成果は手続き定義で表し、能力と手続きを一対一に固定しない。

### 共通意味モデル

共通意味モデルは、領域をまたいで同じ意味を持つ概念と関係を定める。各領域は共通概念を組み合わせ、領域固有の制約と語彙だけを追加する。

共通概念はデータベースの単一巨大テーブルを意味しない。各境界づけられた領域は所有するデータを保ち、安定した識別子と明示した関係で他領域へ参照を公開する。

### 横断統制

横断統制は、すべての業務能力と共通概念に適用する。認証と認可、職務分離、監査、来歴、記録管理、機密区分、外部連携、冪等性、通知を領域ごとに別設計しないための規則を定める。

横断統制は業務状態を所有しない。たとえば通知は業務イベントの結果として作成し、通知の既読状態を申請や承認の正にしない。

## 五軸タグ

「人・時間・物・お金・成長」は、機能を見つけ、説明し、利用者の関心で横断表示するための非排他的なタグである。三層のいずれかを置き換えず、データ所有、集約境界、認可、保存期間を決めない。

各タグは次の関心を示す。

- 人: 個人、組織、所属、役割、関係、ライフサイクル
- 時間: 日時、期間、予定、勤務、期限、利用可能性
- 物: 資産、設備、場所、在庫、利用権、保管と貸借
- お金: 金額、予算、費用、約束、精算、支給結果
- 成長: スキル、学習、目標、評価、対話、キャリア

能力、手続き定義、画面、コマンド、文書には零個以上のタグを付与できる。一つの対象へ複数タグを付けられ、どのタグにも適合しない認証や監査のような横断機能へ無理に付与しない。

タグ値は管理された語彙として扱う。新しいタグを追加するときは、既存タグの言い換えでないこと、検索上の利用目的、付与対象を決定記録へ残す。

個別の申請内容や従業員レコードには、分類の都合だけで五軸タグを複製しない。対象の型と手続き定義から検索タグを導出する。

## 共通概念

共通概念は論理的な語彙であり、現行スキーマのテーブル名とは一致しない場合がある。実装時は領域の責務と整合性を保てる単位へ写像する。

### 主体と組織

- `Party`: 手続きや関係の当事者になれる個人または組織
- `Person`: 従業員、候補者、家族など、必要な範囲で識別する自然人
- `Organization`: 法人、取引先、外部機関など、組織として行為できる主体
- `LegalEntity`: 法域の下で権利と義務の主体として識別する `Organization`
- `OrgUnit`: 部署、部門、チームなど、組織内で責務を持つ単位
- `Site`: 事業所、建物、区画など、組織や資源を配置する場所
- `Job`: 組織上の配置から独立した職務の目的、責任、必要能力
- `Position`: 一つの `OrgUnit` に置かれ、`Job` を具体化する充足可能な職位またはポスト
- `OrgRole`: 所属、職位、案件などの関係の中で主体が担う責任
- `Membership`: 個人または組織が組織単位へ所属する有効期間付きの関係
- `Assignment`: 主体を職位、責務、案件、資源へ割り当てる有効期間付きの関係
- `ReportingRelation`: 上司、部下、責任者など、主体または職位の間の報告関係
- `CostCenter`: 支出や予算の責任を集計する会計上の管理単位
- `Project`: 目的、期間、責任主体、参加者を持つ期限付きの取り組み
- `Account`: システム上で操作する認証主体
- `Identity`: アカウントが利用するログイン手段と外部識別子
- `SystemRole`: 複数の `Permission` をアカウントへまとめて付与するシステム上の役割
- `Permission`: 資源種別に対する操作能力を表し、認可判定で評価する権限

`Person` と `Account` は分離する。システムアカウントは個人を持たずに存在でき、一人が複数のログイン手段を使えるようにする。

外部の個人や組織は、別の汎用型を作らず、`Party`、`Person`、`Organization` の派生と分類で表す。取引関係、雇用関係、家族関係など、社内との関わりは型名ではなく有効期間付きの関係として記録する。

`SystemRole` と `Permission` は「何を操作できる候補か」を表す。`Membership`、`Assignment`、`ReportingRelation` は「誰に対して、どの組織範囲で操作できるか」を表し、案件の `Task` は「いつ、どの案件、ステップ、ラウンド、順序で操作できるか」を表す。いずれか一つだけで許可を決めず、詳細は [[authorization-model|認可モデル]] のスコープ束と案件限定権限に従う。

### 手続きと仕事

- `Capability`: 会社が継続的に果たす責務
- `ProcedureDefinition`: 手続きの目的、入力、参加者役割、工程、成果を定める論理定義
- `ProcedureVersion`: 公開済み定義を固定した版
- `Case`: 特定の対象について開始した手続きの実行単位
- `Participant`: ケースに主体を役割付きで参加させる関係
- `Task`: ケース、ステップ、ラウンド、順序、担当、許可操作、期限、完了条件を持つ作業単位
- `Decision`: 判断者、選択、理由、根拠、時刻を持つ変更不能の判断記録
- `Approval`: 許可、却下、差戻しなどを表す `Decision` の一種
- `Delegation`: 期間、範囲、委任元、代理者を持つ権限委任
- `Policy`: 適用対象、条件、効果、有効期間、版を持つ規則集合
- `Agreement`: 複数の `Party` が合意した条件、版、有効期間、証拠を結ぶ記録
- `Entitlement`: 方針または合意に基づき、主体が利用、受領、要求できる範囲を表す関係
- `Obligation`: 方針または合意に基づき、主体が期限までに果たす責務を表す関係
- `Event`: 既に起きた出来事を記録する変更不能の事実
- `Observation`: ある時点で観測した状態、数量、結果
- `Outcome`: ケースまたは活動が確定した成果

ケースは任意の JSON だけで意味を完結させない。検索、認可、整合性に使う主体、対象、期間、金額、資源、決定は型を持つ共通概念として参照し、領域固有の補足だけを構造化した入力へ置く。

### 資源、時間、価値、記録

- `ResourceType`: 資産、設備、空間、利用権、消耗品などの種類
- `Resource`: 個別に識別または数量管理する対象
- `Place`: 住所、部屋、保管場所、目的地などの位置
- `Reservation`: 将来の期間に資源能力を確保する関係
- `Allocation`: 主体または組織単位へ資源や数量を割り当てる関係
- `Custody`: 資源の保管責任を主体へ結びつける有効期間付きの関係
- `Instant`: タイムゾーンを解決できる一点の時刻
- `LocalDate`: 業務カレンダー上の日付
- `Interval`: 開始と終了を持つ期間
- `Schedule`: 繰り返し、例外、休日、タイムゾーンを含む予定規則
- `Money`: 金額と通貨を組にした値
- `Quantity`: 数値と単位を組にした値
- `Document`: 内容、媒体、版、作成者、保管先を識別できる情報資源
- `Evidence`: 判断、観測、申請を裏づける文書または外部参照
- `Record`: 業務活動の証拠として捕捉し、保持と廃棄を管理する情報
- `Classification`: 機密区分、文書種別、業務分類など、目的を明示した管理語彙

`Money` と `Quantity` は識別子を持つ業務対象ではなく値として扱う。換算、集計、税計算の結果を持つ場合は、使用した外部規則、基準時点、出所を別の事実として記録する。

### 来歴と外部連携

- `Agent`: 人、組織、アカウント、外部システムなど、活動へ責任を持つ主体
- `Activity`: 入力を使用し、出力や変更を生む処理
- `Provenance`: 事実や文書を生成、変更、取得した主体、活動、時刻、元データの関係
- `SourceSystem`: 外部データの正を管理するシステム
- `ExternalReference`: 対象を外部システムの識別子へ結びつける名前空間付き参照
- `SyncRun`: 取込または出力の開始、終了、結果、再実行キーを記録する単位

外部参照は表示名やメールアドレスを識別子の代用にしない。名前空間、外部識別子、対象型、接続先を組にして一意にする。

## 共通関係

関係は外部キーの有無だけでなく、意味、向き、有効期間、作成根拠を持つ。領域をまたぐ参照では、相手の表示用属性を正として複製しない。

- `Organization` は `OrgUnit` を包含し、`OrgUnit` は別の `OrgUnit` の上位または下位になれる
- `LegalEntity` は `Organization` の一種であり、法域と登録識別子を持てるが、法的な有効性の判定を担わない
- `Position` は一つの `OrgUnit` に属して `Job` を具体化し、`Assignment` が `Party` と `Position` を期間付きで結ぶ
- `Membership` は `Party`、`Organization` または `OrgUnit`、業務上の `OrgRole` を結ぶ
- `ReportingRelation` は主体または職位を期間付きで結び、現在関係と記録時点の関係を区別する
- `CostCenter` は責任を持つ `LegalEntity` または `OrgUnit` と関係する
- `Project` は責任主体、参加者、期間、使用する `CostCenter` と関係する
- `Account` は零人または一人の `Person` を表し、複数の `Identity` を持てる
- `SystemRole` は `Permission` を束ね、アカウントへの付与に有効期間と付与根拠を持てる
- `Capability` は複数の `ProcedureDefinition` で実現でき、一つの手続きは複数能力を支援できる
- `ProcedureVersion` は `Case` の開始時に固定され、`Case` は主体、対象、参加者、`Task`、決定、証拠、成果を結ぶ
- `Task` はケース、ステップ、ラウンド、順序、候補者、許可操作、開始時刻、期限、完了条件を結ぶ
- `Delegation` は委任元と代理者を結ぶが、判断記録から実行者と本来の権限者を失わせない
- `Agreement` は当事者、証拠文書、版、有効期間を結び、`Entitlement` と `Obligation` の根拠になれる
- `Reservation`、`Allocation`、`Custody` は `Resource`、主体または組織単位、期間を結ぶ
- `Evidence` は根拠となる `Document` または `ExternalReference` を、ケース、決定、観測へ結ぶ
- `Provenance` は `Agent`、`Activity`、入力、生成物、派生元を結ぶ
- `Policy` は能力、手続き、対象型、操作、有効期間へ適用できる

## 設計上の不変条件

ここで定める不変条件は、新規領域と、変更対象になった既存領域が満たす設計契約である。現行データがすでにすべて満たすという意味ではない。

### 識別と参照

- 業務対象は表示名と分離した安定識別子を持つ
- 人が変更できるコードは名前空間内で一意にし、参照の永続的な意味をコード変更へ依存させない
- 領域間参照は対象型と識別子を組にし、同じ数値 ID が別の型を指す曖昧さを作らない
- 外部参照は接続先と名前空間を含め、外部側の再採番や統合を履歴として扱う

### 時間と履歴

- 期間は開始が終了を超えず、終了を含むか除くかを型ごとに統一する
- 時刻はタイムゾーンを解決できる形式で保存し、業務日付は適用する業務カレンダーを明示する
- 所属、割当、委任、方針は有効期間を持ち、過去の事実を現在値で上書きしない
- 同時に一つだけ許される関係は、対象と期間の重複を永続化境界で拒否する
- 訂正は元の事実を消さず、取消、差替え、訂正元の関係を記録する

### 手続きと判断

- 公開済み手続きは改版し、開始済みケースの `ProcedureVersion` を後から差し替えない
- 状態遷移は許可する前状態、操作、実行者、遷移後状態を定義し、任意文字列の更新にしない
- 決定は判断者、実行アカウント、本来の権限者、選択、理由、根拠、時刻を保持する
- 同一の操作を再送しても二重のケース、決定、割当、支出を作らないよう冪等キーを定める
- 競合する変更は一意制約、条件付き更新、トランザクションのいずれかで直列化する
- ケースの完了条件は必要なタスク、決定、証拠、成果から機械的に判定できる形で定義する

### 認証と認可

- 認証主体、業務上の人、組織上の所属を別概念として評価する
- 認可は主体、対象、操作、環境、方針の属性を評価し、許可規則が成立しない操作を拒否する
- `SystemRole` は属性の一つとして使い、所有者、組織関係、対象状態、案件 `Task`、委任期間などの条件を置き換えない
- 申請者と決定者を分離する手続きでは、本人による決定を拒否する
- 代理操作では代理者だけでなく委任元と委任範囲を検証し、両者を証跡へ残す
- 一覧、詳細、集計、出力の各操作へ同じ情報境界を適用し、集計から非公開対象を推測できないようにする

### 資源と価値

- 排他的な資源予約は同じ資源と期間の重複を拒否し、数量資源は確保量が利用可能量を超えない
- 保管責任の移転は前の `Custody` を閉じてから次を開始し、現在の保有者と履歴を両立させる
- 金額は通貨を伴い、数量は単位を伴う
- 予算、残数、ポイントなどの残高は、元となる付与と消費の事実、または整合性を保つ原子的なカウンタから再現できる
- 外部計算結果は入力、基準時点、算出元、取得時刻を持ち、open-karte が計算法や法的妥当性を保証したように表示しない

### 記録と来歴

- 業務上の決定と監査イベントは追記を基本とし、通常の更新や削除で消さない
- 記録は作成主体、作成活動、作成時刻、対象、機密区分、保持方針を持つ
- 証拠文書はケースの自由記述へ埋め込まず、版と保管先を識別できる参照で結ぶ
- 外部から取得した値は `SourceSystem`、`ExternalReference`、`SyncRun` を追跡できる
- 監査メタデータへ認証情報、秘密値、不要な個人情報を記録しない
- 保存期間の満了、法的保全、本人の権利が競合する場合は、外部の法務判断を入力として処理結果だけを記録する

## 現行実装との対応

現行実装は、三層モデルの一部を複数の個別ドメインで表している。次の対応は理解のための写像であり、統合済みの共通実装を意味しない。

- `employees`、`departments`、`org_departments`、`org_memberships` は、人、組織単位、所属の一部を表す
- `accounts`、`identities`、`roles`、`permissions` は、認証主体、ログイン手段、ロール、権限の一部を表す
- `application_templates`、`applications`、`application_workflows`、承認記録は、手続き定義、ケース、判断の一部を表す
- 勤怠、シフト、休暇、会議室予約は、時間、予定、割当の異なる側面を個別に表す
- 資産、貸出、棚卸し、会議室、レンタル予約は、資源、保管、予約、観測を個別に表す
- 経費、予算、給与明細、サンクスポイントは、金額または数量の事実を個別に表す
- スキル、目標、評価、研修、キャリア、1on1 は、成長に関する事実と手続きを個別に表す
- 通知、ナレッジ、監査ログ、バッチジョブは、連絡、情報、証跡、運用記録の一部を表す

新規領域が既存テーブルを直接再利用できない場合でも、共通概念の意味と関係は揃える。物理統合は、整合性、認可、移行、障害分離の利点が明らかな場合に限る。

## 複合例

複合例は、五軸の一つへ機能を押し込まず、共通概念を組み合わせる方法を示す。いずれも目標表現であり、現行実装の完成状態を示さない。

### 出張を申請する

出張管理の `Capability` を、公開済みの `ProcedureVersion` で実現する。`Case` は出張者である `Person`、訪問先の `Place`、出発から帰着までの `Interval`、概算の `Money`、承認者となる `Participant`、判断の `Approval`、旅程や領収書の `Evidence` を結ぶ。

承認後に経費申請が必要なら、出張ケースと経費ケースを派生関係で結び、同じ自由記述を複製しない。税区分や精算額の計算は外部結果として受け取り、出所を記録する。タグは「人」「時間」「お金」を付与できる。

### 備品を貸し出す

資産管理の `Capability` を、貸出手続きと返却手続きで実現する。個体を `Resource`、利用者を `Party`、予約期間を `Reservation`、実際の保管責任を `Custody`、返却時確認を `Observation` として表す。

貸出開始時は予約の有効性と現在の保管責任を検証し、同じ排他資源の重複利用を拒否する。返却時は前の保管関係を閉じ、状態確認の証拠を残す。タグは「人」「時間」「物」を付与できる。

### 研修を割り当てる

学習管理の `Capability` を、研修定義、受講割当、完了記録で実現する。受講者を `Person`、コースを領域固有の学習資源、期限を `LocalDate`、受講割当を `Assignment`、修了とスコアを `Observation`、獲得した能力をスキル関係として表す。

修了結果を外部学習サービスから取得する場合は、`SourceSystem`、`ExternalReference`、`SyncRun` を残す。タグは「人」「時間」「成長」を付与できる。

### 取引先を確認する

取引先管理の `Capability` を、確認手続きとして実現する。対象を外部の `Organization`、申請者と確認担当を役割の異なる `Participant`、提出資料を `Evidence`、外部調査結果を `Observation`、社内の受付判断を `Decision` として表す。

open-karte は法的な適格性を独自に確定せず、外部結果と社内手続きの事実を分けて記録する。確認担当が申請者本人でないことを認可と不変条件で検証する。

### 育児休業を申し出る

休業管理の `Capability` を、申出受付、必要書類確認、関係者への連絡、復帰準備のタスクで実現する。対象者を `Person`、休業期間を `Interval`、申出を `Case`、提出書類を `Evidence`、期限と担当を `Task` として表す。

給付額や法的な受給資格は外部判断へ委ねる。外部機関へ提出した事実と返却された結果は、文書、外部参照、来歴を伴う記録として保持する。タグは「人」「時間」を付与できる。

## 新しい領域を追加する契約

新領域は、画面やテーブルを追加する前に、業務能力、共通概念、横断統制への写像を定義する。実装提案は次の契約を満たす。

### 能力と境界を定義する

- 能力の安定識別子、目的、利用者が片付ける仕事、対象範囲を記述する
- 既存能力との包含、重複、依存を確認し、画面名や部署名を能力名にしない
- open-karte が保持する事実と、外部へ委ねる計算または判断を分ける
- 五軸タグを零個以上付与し、タグをデータ所有境界に使わない

### 概念と関係を定義する

- 入力、対象、主体、参加者、資源、期間、金額、文書、成果を共通概念へ写像する
- 新しい概念が必要なら、既存概念では保持できない意味と不変条件を説明する
- 領域が所有するデータと、他領域から安定識別子で参照するデータを分ける
- 多対多、有効期間、履歴、派生元を単一の文字列や複製属性へ押し込まない

### ライフサイクルを定義する

- 作成から終了までの状態、許可する遷移、実行者、前提条件、失敗理由を定義する
- 手続き定義の改版方法と、開始済みケースへ適用する版を定義する
- 取消、差戻し、再申請、訂正、期限超過、外部失敗、再実行を通常経路と同じ精度で定義する
- 重複送信と同時更新に対する冪等キー、一意条件、直列化方法を定義する

### 認可と職務分離を定義する

- 操作ごとに主体、対象、操作、環境の必要属性を列挙する
- 所有者、組織関係、`SystemRole`、`Permission`、案件 `Task`、対象状態、委任の各条件をサーバ側で評価する
- 本人、上長、担当者、管理者が閲覧できる範囲と、一覧や集計で見える範囲を揃える
- 申請者と決定者、作成者と確認者など、同一人物を許さない役割の組を定義する
- 代理操作で記録する実行者、委任元、委任範囲を定義する

### 記録と来歴を定義する

- 監査対象となる作成、閲覧、変更、決定、出力、権限変更を定義する
- 証拠、添付、生成文書の版、機密区分、保管先、保持方針を定義する
- 個人情報と機密情報を必要最小限にし、ログと通知へ複製する範囲を定義する
- 訂正前の値、変更主体、変更理由、変更時刻を追跡できるようにする

### 外部連携を定義する

- 各項目の正を open-karte と外部システムのどちらが持つか定義する
- 外部識別子の名前空間、同期方向、取得時刻、再実行キー、失敗時の回復方法を定義する
- 外部計算または判断の入力、結果、版、出所を分離する
- 外部停止時に受け付ける操作と、回復後に整合させる方法を定義する

### インタフェースと検証を定義する

- API を業務操作と認可判定の正本にし、利用者の仕事と実装状況に応じて CLI と Web の提供面を選定する
- 複数の提供面に出す同一操作は、意味、入力、出力、状態遷移、失敗理由を揃える
- 資源名、状態遷移、入力と出力を既存の URL 規約と型生成の流れへ合わせる
- 正常経路だけでなく、認可拒否、重複、競合、境界日付、外部失敗、訂正履歴を検証する
- スキーマ、ドメイン、手続き、認可、監査、利用者向け機能文書を同じ変更で更新する

新領域の完成条件は、機能が動くことだけではない。共通概念の再利用理由、領域固有概念の必要性、不変条件、認可、証跡、外部境界を第三者がコードと文書から一致して確認できる状態を完成とする。
