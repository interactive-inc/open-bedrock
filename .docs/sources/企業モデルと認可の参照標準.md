# 会社メタモデルを設計するための参照理論と標準

規範性: 根拠記録。非実行の調査 snapshot。製品固有の意味と制約は仕様正本を優先する。

この文書は、open-karte の会社メタモデルで参照する外部理論と標準、その採用目的を記録する。語彙と設計観点を選択的に利用し、各標準への完全準拠、認証、交換互換を主張しない。

## 採用原則

- 概念の意味と不変条件は [会社メタモデル](../company-model.md) に定義する。
- 標準の class 名、形式、適合要件を実装済みと推定しない。
- 標準の更新を自動採用せず、意味変更は decision record と migration を通す。
- 法令、規程、契約、専門判断を一般標準だけで置き換えない。
- 圏論は意味を発明する理論ではなく、定義済みの意味を保つ合成の検査に使う。

## 基礎存在論

[Unified Foundational Ontology の博士論文](https://research.utwente.nl/en/publications/ontological-foundations-for-structural-conceptual-models/) と [OntoUML Vocabulary](https://w3id.org/ontouml-models/vocabulary) は、Kind、Role、Phase、Relator、Event などを区別する基礎として参照する。

採用目的は、人と従業員、資源と予約対象、組織と役職など、本質的な型と文脈依存の役割を混同しないことである。OntoUML の図式、tool、全 stereotype への準拠は要求しない。

## 圏論と database

[Ologs: a categorical framework for knowledge representation](https://arxiv.org/abs/1102.1889) は、型と関係を圏として捉え、可換図式で知識の一貫性を考える方法を参照する。

[Functorial Data Migration](https://arxiv.org/abs/1009.1166) は、schema を圏、instance を Set への関手として捉え、schema mapping と data migration を合成する方法を参照する。

採用目的は、共通核と domain module の結合、内部 schema と外部 API の mapping、path independence、migration の意味保存を検査することである。category database をそのまま runtime として採用することや、圏論だけで業務意味と安全性を証明することは要求しない。

## 組織

[W3C Organization Ontology](https://www.w3.org/TR/vocab-org/) は、Organization、OrganizationalUnit、Membership、Role、Post、Site の語彙を参照する。

open-karte は、合議体と一人役職、組織責任と IAM permission をさらに分離する。RDF、OWL、linked data 公開は採用条件にしない。

## 時間

[W3C Time Ontology in OWL](https://www.w3.org/TR/owl-time/) は、instant、interval、duration、temporal relation の語彙を参照する。

採用目的は、valid time、recorded time、policy effective time を区別し、期間境界を一貫させることである。OWL reasoner の導入は要求しない。

## 来歴

[W3C PROV-O](https://www.w3.org/TR/prov-o/) は、Entity、Activity、Agent と、generation、usage、derivation、attribution、delegation の語彙を参照する。

採用目的は、申請、判断、AI 提案、外部取込、mapping、訂正の source と actor chain を追跡することである。既存 audit log だけで PROV-O 適合を主張しない。

## policy と権利表現

[W3C ODRL Information Model](https://www.w3.org/TR/odrl-model/) は、permission、prohibition、duty、constraint、party、asset を含む policy 表現の参考にする。

採用目的は、許可、禁止、義務と制約を事実状態から分けることである。ODRL policy をそのまま API 認可 engine として実行せず、会社上の authority、TechnicalPermission、CaseAssignment を open-karte で明示する。

## 認可

[NIST SP 800-162](https://csrc.nist.gov/pubs/sp/800/162/upd2/final) は、subject、object、operation、environment の属性と policy による ABAC を参照する。

採用目的は、role だけに依存せず、Principal、resource、relation、state、time、purpose、field を合成することである。NIST の特定組織向け適合や認証は主張しない。

## constraint

[W3C Shapes Constraint Language](https://www.w3.org/TR/shacl/) は、graph-shaped data の constraint と validation report の考え方を参照する。

採用目的は、domain extension、参照整合、外部 mapping の能力質問と反例を機械検査へ落とすことである。RDF graph と SHACL engine の採用は要求しない。

## process

[OMG Business Process Model and Notation](https://www.omg.org/spec/BPMN/2.0.2) は、event、activity、gateway、participant、message、sequence を参照する。

採用目的は、ProcedureDefinition と ProcedureCase の流れを説明することである。BPMN execution engine、XML 交換、全適合 class は要求しない。

## capability

[OMG Business Architecture Core Metamodel](https://www.omg.org/spec/BACM/1.0) は、capability、outcome、organization、value stream の関係を参照する。[APQC Process Classification Framework](https://www.apqc.org/process-frameworks) は、会社能力の漏れを点検する外部 checklist として参照する。

能力を組織、process、system から独立させる観点を採用するが、分類番号の互換、全 process の実装、認定は主張しない。

## record management

[ISO 15489-1:2016](https://www.iso.org/standard/62542.html) は、record、record metadata、policy、responsibility、control、capture、management の原則を参照する。

採用目的は、申請、判断、証拠、生成文書、audit を後から説明できる record として管理することである。保持期間と廃棄可否は ISO だけから決めず、法域、契約、公開済み規程、legal hold を入力とする。

## 役割分担

UFO と OntoUML は概念の同一性、圏論は理論と mapping の合成、W3C ORG は組織、OWL-Time は時間、PROV-O は来歴、ODRL は規範語彙、NIST ABAC は技術認可、SHACL は constraint、BPMN は手続き、BACM と APQC は capability、ISO 15489 は record management を補助する。

同じ語が複数標準に現れる場合、open-karte の定義を優先する。外部交換仕様を実装する場合だけ、対象標準への写像、loss、適合範囲を別 decision と connector contract に定める。
