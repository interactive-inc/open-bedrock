# 認可モデル

この文書は、open-karte における認可の目標仕様を定める永続的な正本である。認証基盤を IAM へ移した経緯は [IAM 認証・認可システムの移行履歴](./iam-auth-design.md) に残し、認可判断の規範と現行実装との差分はこの文書で管理する。

## 文書の位置づけ

この文書の「目標仕様」は、新規実装と既存機能の改修が満たす規範である。「現行実装との差分」は、監査時点のコードが規範を満たしていない箇所を示す。実行時の挙動についてはコードが事実であり、コードを変更したときは差分記録も同じ変更で更新する。

認可は、ロール名だけでは決めない。システム権限、組織関係、自己所有、案件割当、委任、緊急権限を、対象資源、操作、項目、時刻、状態と組み合わせて判断する。

## 目標仕様

### 認可判定の規範

API が認可判定の正本である。Web と CLI は操作を見つけやすくするために権限情報を利用できるが、表示されたこと、非表示だったこと、クライアント側検査を通過したことを認可根拠にしてはならない。すべての API 操作は、直接リクエストされた場合にも同じ判定を行う。

認可の既定は拒否とする。必要な情報を取得できない場合、権限キーを解釈できない場合、関係や時刻が曖昧な場合、監査を確実に記録できない特権操作は、許可へ倒さない。

認可判定は次の合成で表す。

```text
システム付与 = システム権限を持つ AND 組織スコープ内である
自己付与 = 自己操作ポリシーがある AND 対象を自己所有している
案件付与 = 有効な案件タスクがある AND 対象・操作・ステップ・ラウンドが一致する
委任付与 = 有効な委任がある AND 委任元の案件付与を同じ範囲で代理する
緊急付与 = 有効な緊急権限がある AND 指定された対象・操作・項目の範囲内である
時間有効性 = 利用するロール付与、組織関係、案件タスク、委任、緊急権限が操作時点で有効である

許可 = 認証済み
  AND アカウントと従業員が操作可能な状態
  AND 対象の状態遷移が操作を許す
  AND 時間有効性を満たす
  AND 項目ポリシーが応答または更新を許す
  AND 職務分離と定足数の規則を満たす
  AND (システム付与 OR 自己付与 OR 案件付与 OR 委任付与 OR 緊急付与)
```

システム権限は操作能力を表し、それだけで対象範囲を表さない。組織全体を対象にする権限では、組織スコープを全社として明示する。自己所有と案件割当は、システム権限の欠落を一般的に補う仕組みではなく、資源ごとに定義された限定付与である。

### スコープ束

認可根拠は裸の権限キーではなく、次の要素を持つスコープ束として扱う。

```text
スコープ束 = {
  主体,
  操作,
  資源種別と資源識別子,
  組織関係,
  許可する項目集合,
  有効時間,
  案件・ステップ・ラウンド,
  根拠の種別と識別子
}
```

組織スコープには、なし、直下の部下、管理連鎖、担当部署、全社を設ける。直下の部下は管理連鎖に含まれ、管理連鎖と担当部署は全社に含まれる。自己と案件は組織スコープと独立しており、自己または一件の案件を許可したことから担当部署や全社へ範囲を広げない。

複数のスコープ束を持つ場合は、各束が許可する対象の和集合だけを利用する。ロール名の包含関係、画面の親子関係、一覧を閲覧できた事実から、より広いスコープを推測しない。関係を一意に解決できない場合は、その束を無効として扱う。

### データ分類と項目ポリシー

資源単位の閲覧権限だけでなく、返却または更新できる項目集合を分類する。同じ資源の一覧、詳細、更新、履歴で項目集合を明示し、一覧権限から詳細項目を推測しない。

- 社内ディレクトリ情報は、在籍中の氏名、従業員コード、部署、役職など、一般業務で検索に必要な項目に限る。
- 業務限定情報は、申請本文、金額、備品のシリアル番号や保有者など、担当業務または明示された管理権限が必要な項目とする。
- 人事機微情報は、休暇理由、勤怠時刻、評価回答、給与関連記録など、自己、案件担当、限定された組織関係、専用の全社権限に絞る。
- 特権情報は、認証主体、ロールと権限、委任、緊急権限、監査証跡など、専用の特権操作として扱う。

API の各ルートは、操作対象の分類、許可するスコープ束、返却または更新する項目集合を一つのポリシーとして定義する。識別子、氏名、コメント、自由記述も分類対象であり、内部 ID だから安全、表示名だから安全とはみなさない。

### システム権限と組織関係

システム権限は、アカウントに付与された有効なロールの権限集合からリクエスト時に解決する。JWT や UI に残った古い権限集合を利用しない。停止中またはロック中のアカウント、退職済みの従業員、存在しない権限キーは付与を生まない。

組織関係は、対象者に対する直属管理者、管理連鎖上の管理者、部署責任者などの関係として解決する。資源ポリシーは、現在時点の関係を使うか、記録時点の関係スナップショットを使うかを明示する。現在の組織表しか存在しない場合に、過去時点の関係が必要な操作を許可しない。

自己所有は、申請者、記録対象者、予約者など、資源ごとに定めた所有者識別子との一致で判断する。自己所有から他者の記録、同じ部署の記録、関連する別資源への権限を導出しない。

### ワークフローの案件限定権限

承認候補者セレクターは候補者を選ぶ規則であり、候補者に全社的なシステム権限を付与する規則ではない。承認ステップを開始した時点で案件タスクを作成し、その案件タスクだけが承認、却下、差し戻しなどの操作を許可する。

ワークフロー定義の作成、改版、公開にはテンプレート管理権限を要求する。定義が参照するロール、従業員、組織関係、条件の型を公開前に検証し、未知の参照を含む定義は保存しない。公開済みの版だけを新しい申請へ適用する。

案件タスクは、申請識別子、ワークフロー定義の版、ステップ、ラウンド、許可操作、候補者、開始時刻、期限、定足数を持つ。現在のステップと一致しないタスク、終了したラウンドのタスク、決定済みのタスクは利用できない。

ワークフロー定義は申請時に固定し、候補者集合は各ステップの開始時に固定する。候補者スナップショットには、候補者のアカウントと従業員の識別子、候補者となったセレクター、参照したロールまたは組織関係、解決時刻、定足数を保存する。ロール付与や組織変更は進行中ステップの候補者と定足数を書き換えず、後続ステップの開始時にだけ反映する。

候補者が不在、停止、退職などで操作できなくなった場合は、暗黙の再解決を行わない。再割当、期限超過時のエスカレーション、案件取消のいずれかを明示的な状態遷移として記録する。

### 委任

委任は、委任元が候補者として持つ案件限定権限を、指定した代理人が同じ範囲で行使する仕組みである。委任によってシステム権限、組織スコープ、対象項目、対象テンプレート、許可操作を拡張しない。委任の連鎖と自己への委任は許可しない。

委任の有効期間は UTC の時点へ正規化し、半開区間で評価する。

```text
starts_at <= now AND now < ends_at
```

入力はタイムゾーンオフセットを含む ISO 8601 として解析し、文字列の辞書順では比較しない。開始時刻が終了時刻以上の入力、実在しない時刻、解釈できないオフセットは拒否する。重複期間の検出も UTC の時点で行い、境界が接する二つの半開区間は重複とみなさない。

決定記録には、実際に操作した主体と、代理された候補者の両方を保存する。委任の取消は将来の操作だけを無効にし、取消前に確定した決定の根拠を消さない。

### 緊急権限

緊急権限は通常の管理者ロールとは別の、短時間かつ目的限定の付与とする。対象資源、操作、項目、有効期限、理由、付与者、承認者を必須とし、自分自身への付与を許可しない。単独の緊急権限で職務分離や複数人の定足数を無効にしない。

緊急権限の発行、使用、延長、取消は監査へ記録し、指定された通知先へ通知する。監査記録の変更や削除、権限モデル自体の恒久変更は緊急権限の対象外とする。期限切れは非同期処理を待たず、認可判定時に即時無効として扱う。

### 職務分離と定足数

職務分離はロール名ではなく、申請者、資源所有者、候補者、実行者、代理された候補者、ロール付与者などの主体識別子で検査する。

- 申請者または資源所有者は、自分の案件を承認、却下、差し戻しできない。
- ロール管理者は、自分へのロール付与と、自分だけを残す特権縮小を実行できない。
- 機微な作成と確定を分離する資源では、同じ主体が両方を担当できない。
- 定足数は候補者スナップショットに対して計算し、進行中に候補者数が変わっても再計算しない。
- 一つのステップで一人の実行者が数えられるのは一票までとする。同じ代理人が複数の候補者から委任を受けても、複数票として数えない。
- 最後の実効管理者を失うロール編集、ロール剥奪、アカウント停止、従業員退職を拒否する。

定足数の達成は、必要票数、異なる実行者数、異なる代理元候補者数をすべて検査する。並行操作では、決定記録の追加とステップ遷移を同じ原子的境界で確定する。

### 履歴参照

承認、却下、差し戻し、委任、ロール付与などの履歴は、後から認可根拠を再現できる事実として保存する。従業員やアカウントを通常表示から除外しても、履歴を物理削除せず、主体識別子と当時の表示用スナップショットを保持する。参照先を消す必要がある場合は、匿名化した主体を示す墓標へ置き換える。

履歴を返す資源は、参照モードとして自己、案件参加者スナップショット、記録時点の組織関係、現在の組織関係、専用の全社履歴権限のいずれかを明示する。モードが定義されていない場合は拒否する。現在の管理者になっただけで過去の機微情報を自動的に閲覧させず、過去の管理者だった事実だけで現在の記録を閲覧させない。

決定の正当性は決定時点の候補者、委任、組織関係、権限、案件状態で評価する。現在の組織やロールを再解決して、過去の決定を有効または無効へ書き換えない。

### 監査

監査記録は追記専用とし、業務記録と監査記録を同じトランザクション、または欠落を防ぐ永続的なアウトボックスで確定する。監査記録に失敗した特権変更、承認決定、委任、緊急権限の操作は成功として返さない。

監査記録には少なくとも次を含める。

- イベント識別子、発生時刻、リクエスト識別子
- 実行アカウントと従業員、代理された候補者、委任識別子
- 操作、対象資源の種別と識別子、変更前後の状態
- 利用した権限、スコープ束、案件タスク、ポリシー版
- 許可または拒否の結果と理由コード
- 緊急権限の識別子と理由
- 必要最小限の接続元情報とクライアント情報

ロールとアカウントの変更、従業員の退職または削除、承認と差し戻し、委任、緊急権限、機微情報の一括取得は必ず記録する。高リスク操作の拒否も記録する。監査の閲覧自体を特権操作として監査し、保持期間中の更新と削除を通常 API から提供しない。

### API と UI の境界

UI のメニュー、コマンドパレット、ボタンの表示制御は補助である。UI は API が返す実効権限と案件タスクを使い、利用できない操作を隠すか理由付きで無効にできる。UI が操作を表示しても API の拒否を上書きできず、UI が操作を隠しても API の案件限定権限を失わせない。

受信箱の導線は、全社的な承認権限だけでなく、現在割り当てられた案件タスクの有無を扱う。サイドバー、コマンドパレット、ページ、Server Action は同じ適格性の意味を共有し、最終判断は常に API で行う。

### 拒否と障害時の既定

認証情報の欠落は認証エラー、認証済み主体の権限不足は認可エラー、並行更新や状態遷移の競合は競合エラーとして区別する。資源の存在を知らせること自体が機微な場合は、認可されない主体へ存在の差を返さない。

権限解決、組織関係、候補者スナップショット、委任時刻、職務分離、監査確定のいずれかに失敗した場合は拒否する。キャッシュや副次サービスが利用できないことを理由に、前回の広い権限やロール名だけの判定へ退避しない。

## 現行実装との差分

この節は、現行コードを監査して確認した目標仕様との差分である。各差分は、関連コードを変更する際に解消状況とともに更新する。

### 経費と休暇の詳細における組織スコープ（解消済み）

経費詳細と休暇詳細は、本人、全社閲覧権限、組織管理権限、または承認権限と管理連鎖・部署責任者の組み合わせだけを許可する。`api/src/interface/expense/[id]/route.test.ts` と `api/src/interface/leave/requests/[id]/requests-crud.test.ts` は、同じ承認権限を持つ管理者でも対象者が組織スコープの内外にいる場合に結果が分かれることを検証する。

### ワークフロー候補者のライブ再解決（解消済み）

`api/migrations/0011_workflow_step_snapshots.sql` は、ステップとラウンドごとの必要票数、開始時刻、期限、解決理由と、候補者の従業員・アカウント、候補者セレクター、エスカレーション開始時刻、解決時刻を保存する。申請時、次ステップへの遷移時、差戻し後の再申請時に候補者を固定し、承認、詳細、受信箱は同じスナップショットを参照する。

移行前から進行中の申請だけは、最初の参照または決定時に候補者を一度だけ解決し、`legacy_backfill` として区別して保存する。定足数到達は保存済み必要票数と承認記録の実数を条件に原子的に遷移し、同時に最終票が入っても申請が承認待ちのまま残らない。`api/src/application/application/workflow-application.test.ts` は、組織変更後も開始時候補者が変わらないこと、並行承認、移行前申請の補完を検証する。

差戻し後の再申請と、一度通過した後続ステップへの再到達は、ステップごとに過去の最大値より大きいラウンドを割り当てる。旧ラウンドの候補者と票は新しい定足数へ混入しない。承認記録の追加直後にも変更行を検査し、無効または重複した票だけで状態遷移を進めない。

### 互換用の approver_roles（解消済み）

ワークフローインスタンスがない移行前の申請は、`application:approve`、テンプレートに設定したロールとの完全一致、申請者に対する管理連鎖または部署責任者の関係をすべて要求する。`org:manage` は組織スコープを全社として扱う。テンプレートの作成と変更では、存在しないロールを拒否する。

設定済みワークフローでは、この互換経路を使わず、保存済みのステップ、ラウンド、候補者スナップショットから案件限定権限を判定する。詳細、受信箱、件数集計、承認と否認は同じ適格性条件を共有する。

### ワークフロー定義の並行更新と来歴（解消済み）

`api/migrations/0012_workflow_definition_revisions.sql` は、現在の定義へ改版番号と更新アカウントを追加し、各版を追記専用の `application_workflow_revisions` に保存する。更新と版の保存は同じ D1 batch で確定し、履歴の更新と削除はトリガーで拒否する。

API、Web、CLI は取得した改版番号を更新時に指定する。先に別の更新が確定した場合は `workflow_revision_conflict` として拒否し、後勝ちで変更を失わせない。実行主体は従業員識別子ではなく認証済みアカウント識別子で保存する。

### 従業員登録時のロール付与（解消済み）

従業員登録で member 以外のロールを指定するには `employee:assign_role` を要求する。加えて、対象ロールの権限集合が登録者の実効権限の部分集合であることを確認する。従業員、アカウント、identity、ロール付与を作成する原子的処理内でも同じ包含関係を再検査し、ロールの並行改版や消失が起きた場合は全体を取り消す。付与記録には実行アカウントを保存する。

### 監査ログと削除される履歴

`audit_logs` は `api/migrations/0003_iam.sql` と `api/src/schema.ts` に定義されているが、業務処理からの書き込みは確認できない。たとえば `api/src/application/iam/grant-account-role.ts` と `api/src/application/iam/update-role.ts` は特権変更を行うが、監査記録を同時に確定しない。

`api/src/application/employee/delete-employee.ts` は、経費承認、申請承認、休暇、勤怠、評価など多数の履歴を削除し、一部の承認者参照を空へ変更する。`api/src/application/employee/employee-crud.test.ts` もこの削除と参照消去を現在の期待値としている。追記専用監査と履歴参照の規範に合わせ、主体の無効化または匿名化と事実の保持へ移行する必要がある。

### 最後の実効管理者（解消済み）

最後の管理者はロールキーではなく、`employee:assign_role`、`iam:manage_roles`、`iam:assign_roles`、`account:manage` をロールの和集合として持つ、ログイン可能なアカウントとして判定する。ロール編集と剥奪、アカウント停止、従業員退職と削除は、操作後にも該当主体が一人以上残ることを同じ原子的処理内で検査する。

### 委任時刻と重複（解消済み）

委任時刻はオフセット付き ISO 8601 を UTC に正規化し、`starts_at <= now AND now < ends_at` の半開区間で評価する。作成時の重複検査と保存は一つの条件付き INSERT で行い、全テンプレート委任とテンプレート限定委任の交差も拒否する。候補者解決と承認確定は同じ期間規則を使う。

正規化導入前に保存されたオフセット付き時刻は migration で UTC へ変換する。解釈不能または開始と終了が逆転した既存行は取消済みとして隔離し、認可根拠に利用しない。

### 委任取消の履歴保持（解消済み）

取消は委任レコードを物理削除せず `cancelled_at` を保存し、将来の承認だけを無効にする。承認記録は実行アカウント、代理された従業員、利用した委任識別子を保持する。承認確定時には委任元、代理人、対象テンプレート、期間、取消状態を原子的に再検査する。

### 緊急権限

目標仕様で定めた緊急権限は、現在の API、Web、CLI、migration にデータモデル、発行、承認、利用、取消、監査の実装がない。通常の管理者ロールを緊急権限の代替として扱うと、目的、対象、項目、有効期限、二者承認を限定できない。

緊急権限を導入するまでは、存在しない緊急付与を認可根拠にせず、通常の権限とスコープで拒否または許可する。導入時は発行から事後確認までを一つの監査可能な能力として実装する必要がある。

### ルートごとの項目範囲（解消済み）

従業員一覧、詳細、変更と勤怠一覧は、`org:manage` では全社、そうでなければ本人と現在の管理連鎖・担当部署に限定する。一覧のデータと総件数には同じ条件を適用し、対象外の従業員の存在を詳細 API の応答差から知らせない。

資産のシリアル番号、購入日、保有者識別子は `asset:manage` または現在の保有者だけへ返す。終了済み評価は、対象者と `review:administer` には全フォームを返し、保存された評価者には本人が提出したフォームだけを返す。現在の組織関係を過去の参加資格として再解決せず、投影後のフォームだけから件数と平均を計算する。

完了済みの移行前申請は、申請者、`application:read:all`、または保存済み承認記録の参加者だけが本文と履歴を閲覧できる。完了後に取得したロールや組織関係から過去の閲覧権限を導出しない。

### コマンドパレットと案件限定権限（解消済み）

申請受信箱の一覧と件数は同じ候補者、委任、互換経路の条件を共有する。Web のコマンドパレットは `application:approve` の保持だけでなく、現在の受信箱件数が一件以上ある場合にも導線を表示する。固定権限を持たない案件候補者でも操作へ到達でき、最終認可は API が行う。

差戻し中は申請の現在ステップとワークフローインスタンスの現在ステップが一致しないため、一覧と件数のどちらにも承認可能案件として含めない。

### 停滞ワークフローの修復（解消済み）

候補者不在などで進められないステップは、暗黙に再解決せず修復一覧へ出す。`application:read:all` と `application_template:manage` の両方を持つ主体だけが、理由と新しい候補者を指定して新ラウンドへ再割当できる。修復操作は Web と CLI から利用でき、前の候補者スナップショットと修復イベントを保持する。

期限を過ぎたステップは、修復可否の判定より先に保存済みエスカレーションを有効化する。保存済み定足数は再割当後も維持する。スナップショットが欠落した全員承認だけは、候補者数と一致する必要承認数を操作者が明示し、理由、操作者、定足数上書きを同じ修復イベントへ記録する。

## 適合確認

認可に関わる変更では、正常系だけでなく次を自動検査する。

- 同じシステム権限を持つ組織スコープ内外の主体で結果が分かれること
- 自己、案件、組織、全社の各スコープ束が意図せず相互に拡張されないこと
- 一覧、詳細、更新、履歴が定義された項目集合だけを扱うこと
- ロールや組織を変更しても進行中ステップの候補者と定足数が変わらないこと
- 異なるオフセットで同じ時点を表す委任と、半開区間の両境界を正しく判定すること
- 自己承認、同一人物による定足数の水増し、最後の実効管理者の喪失を拒否すること
- 特権変更と承認決定で、業務結果だけが残る状態または監査だけが残る状態を作らないこと
- 従業員やアカウントの無効化後も、履歴の主体と当時の認可根拠を再現できること
- UI を経由しない API 呼び出しでも同じ拒否が行われ、案件候補者の導線が固定権限だけで失われないこと
